Resumen Ejecutivo

BEOFLOW ahora tiene una base nueva para convertirse en una plataforma operativa de food-service, no una aplicación limitada a pizza. La pizza shop puede ser la primera implementación, pero la arquitectura ya está pensada para cafés, bares, room service, banquetes, pool service, food courts y múltiples restaurantes dentro de un hotel o casino.

La actualización introduce un Orders Engine modular que centraliza pedidos, estaciones de cocina, flujo KDS, POS, restaurantes y futuras capas de analytics e inventario.

Multi-restaurante KDS realtime Tablet ordering POS workflow Hospitality operations Casino / hotel ready

Qué Se Construyó

Orders Engine modular

Se agregó una estructura backend separada por módulos: orders, kitchen, tablet-ordering, POS, analytics, restaurants y staff.

Interfaces separadas

Se prepararon pantallas dedicadas para customer ordering, KDS y POS, evitando saturar el dashboard principal de BEOFLOW.

PostgreSQL escalable

Se diseñaron tablas universales para restaurantes, pedidos, items, estaciones de cocina, roles y auditoría de estados.

Socket.io realtime

El motor emite eventos en vivo cuando se crean pedidos, cambian estados, se actualiza cocina o POS cierra una orden.

KDS corregido

Los pedidos creados desde /order ahora aparecen automáticamente en /kds, se filtran por restaurante/estación y excluyen órdenes cerradas.

Conceptos universales

Se evitaron campos hardcodeados como pizza size, toppings o pizza station. Ahora se usan modifiers, options, categories y kitchen stations.

Flujo Operativo Universal

Todos los restaurantes usan el mismo ciclo operativo. Esto permite manejar pizzas, bebidas, café, postres, burgers, room service o banquetes sin crear lógica separada por negocio.

Rutas y Eventos Clave

API

  • POST /api/tablet-ordering/orders crea pedidos desde tablet/customer UI.
  • GET /api/kitchen/orders carga tickets activos para KDS.
  • GET /api/kitchen/orders?restaurantId=&stationId= filtra por restaurante y estación.
  • PATCH /api/orders/:orderId/status avanza estados operativos.
  • PATCH /api/pos/orders/:orderId/payment actualiza pago.
  • POST /api/pos/orders/:orderId/close cierra la orden.

Socket.io

  • orders:created cuando nace una orden.
  • orders:status_changed cuando cambia el estado operativo.
  • kitchen:order_status_changed para KDS.
  • kitchen:item_status_changed para items de cocina.
  • pos:payment_status_changed para pagos.
  • orders:closed cuando POS cierra una orden.

Corrección Más Reciente: KDS

El problema era que el backend sí guardaba y devolvía los pedidos activos, pero la pantalla KDS no estaba escuchando los eventos realtime y podía esconder tickets por filtros viejos de restaurante o estación.

Antes Ahora
El KDS dependía de refresh manual o podía quedarse sin actualizar. El KDS escucha eventos realtime y también tiene polling de respaldo.
Los filtros podían pedir una lista vacía si cambiaba restaurante/estación. Se carga la cola activa completa y se filtra localmente de forma consistente.
No había suficiente logging para ver el flujo. Hay logs de creación de orden, consulta KDS, status counts y realtime events.

Roadmap de la Nueva Actualización

Fase 1 · Base

Orders Engine foundation

Crear la estructura modular, schema base, rutas principales, pantallas separadas y flujo universal de pedidos.

Estado: base creada y lista para seguir endureciendo.

Fase 2 · Estabilidad

Producción controlada

Revisar auth, roles, permisos, seed data, logs, manejo de errores, deploy en Render, QA del flujo order → KDS → POS y limpieza de datos de prueba.

Resultado esperado: demo funcional estable para una primera operación real.

Fase 3 · Operación

KDS y POS completos

Agregar routing por estación, timers, prioridad, item-level prep, recibos, refunds, voids, cierre de caja y reportes básicos de ventas.

Resultado esperado: flujo operativo usable por cocina y cashier.

Fase 4 · Multi-venue

Hoteles, casinos y múltiples restaurantes

Soportar Pizza Shop, Bar, Coffee Shop, Buffet, Pool Kitchen y Room Service compartiendo el mismo backend, filtros, analytics y permisos.

Resultado esperado: operación multi-restaurante desde un solo sistema.

Fase 5 · Enterprise

Integraciones e inteligencia operacional

Inventario auto-deduction, QR ordering, mobile ordering, room delivery, Apple Watch notifications, comp workflows, banquet/BEO sync y AI operational insights.

Resultado esperado: plataforma tipo hospitality enterprise, comparable en filosofía a Toast, Micros o Square Restaurant.

Próximas Decisiones

Primer venue real

Definir si la primera prueba será Pizza Shop, Bar, Coffee Shop o Room Service.

Roles y accesos

Separar permisos para admin, manager, cashier, kitchen y tablet/customer.

Data operativa

Crear restaurantes, estaciones, items y modifiers reales para pruebas.

Recomendación: mantener BEOFLOW como centro administrativo y operar pedidos en apps dedicadas. Esto evita saturar el dashboard y permite que cada pantalla sea rápida, clara y diseñada para su usuario: cliente, cocina, cashier o manager.

Cómo Probar la Actualización

  1. Entrar a BEOFLOW y confirmar que el dashboard principal sigue funcionando.
  2. Abrir /order para crear un pedido desde la interfaz de customer/tablet.
  3. Abrir /kds y confirmar que el ticket aparece en NEW sin duplicar storage.
  4. Avanzar el ticket por ACCEPTED, PREPARING y READY.
  5. Abrir /pos, actualizar pago y cerrar la orden.
  6. Confirmar que órdenes CLOSED ya no aparecen en la cola activa de cocina.
  7. Probar filtros de restaurante y estación para validar operación multi-venue.
